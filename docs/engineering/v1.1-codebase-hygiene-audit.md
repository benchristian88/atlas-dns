# Atlas DNS Controller v1.1.0 codebase hygiene audit

Audit date: 2026-08-27  
Audited commit: `71882ae9a4fecd528042e5108a585c5cef7a7ca2`  
Audited branch: `docs/1.1-codebase-hygiene-audit`  
Scope: forensic, read-only review of the repository before the v1.1.0 release candidate

## 1. Executive summary

The repository is **moderately burdened**, not significantly burdened. The production paths are coherent, the documented architectural boundaries are enforced, all repository-supported build and unit checks pass, no called Go vulnerability or npm production vulnerability was found, and no abandoned database table or obsolete public API was proven. The material debt is concentrated in a small number of dead scaffolds and exports, stale active documentation, duplicated presentation and compatibility helpers, and several large safety-sensitive functions and frontend pages.

No genuine security, data-loss, upgrade, or incorrect-runtime release blocker was found. Before the release candidate, the highest-value work is documentation correction and low-risk removal of indisputably dead artifacts. Larger consolidation and complexity work should be separate post-1.1 changes.

The migration history is not cleanup material. All migrations `000001` through `000019` are part of clean installation, checksum verification, rollback lookup, and the released-upgrade chain. They must remain unchanged. Any database cleanup must be a new append-only migration.

This audit changed only this document. It did not implement any finding.

### Entry points and dynamic reachability

The Go application/maintenance entry points are:

1. `cmd/controller`: production HTTP application and worker host.
2. `cmd/migrate`: explicit database migration command.
3. `cmd/atlas-dns-backup`: create, preflight, and restore operations.
4. `cmd/atlas-dns-admin`: administrative MFA reset.
5. `cmd/forwarder`: a nonfunctional future scaffold, not included in release builds.

The controller registers 13 named worker states: node connectivity, DNS service health, AdGuard release check, notification delivery, statistics collection and retention, query-log collection and retention, operational-history retention, deployment, operational commands, drift reconciliation, and session cleanup. Some worker states share a polling loop, but each is an operator-visible runtime responsibility.

The frontend enters at `web/src/main.tsx`, then `App`, route resolution, and `ApplicationShell`. It has 30 canonical paths and six deliberate legacy redirects. Pages are statically imported; no lazy page chunks currently exist.

The only generated/dynamic mechanism found is `//go:embed *.sql` for migrations. There is no `go:generate`, runtime plugin framework, reflection-based registration, or dynamic module loading that would invalidate ordinary reachability analysis. `web/public/theme-init.js` is loaded directly by `web/index.html`, so TypeScript-only analysis cannot see it.

The server registers the versioned external API under `/api/v1`. The route inventory was checked against `docs/api/controller-api.md`, handler registration, route tests, and the typed frontend client. Absence of a frontend caller was not treated as proof that a documented API is obsolete.

## 10. AI/over-abstraction findings

The repository does not contain a generic plugin framework, speculative event bus, general-purpose repository framework, or generated abstraction layer without a current consumer. Most interfaces and DTO boundaries have a defensible test, infrastructure, security, or API role.

- **SIMPLIFY:** `api.Server` has roughly two dozen service fields populated through `NewServer` plus many `SetX` methods. - **INVESTIGATE:** the empty E2E scaffold and the nonfunctional forwarder are the only clear speculative scaffolds. The forwarder should be removed; the E2E gap should be handled as test planning, not as a runtime framework.

## 18. Migration-history findings

The runner embeds every `*.sql` migration, parses numeric identities, computes the SHA-256 checksum of each up migration, takes an advisory lock, verifies applied checksums, and applies pending migrations transactionally. Tests require a contiguous set whose latest version is 19. Development rollback also resolves the historical file. Backup manifests record schema compatibility and restore validation uses it.

Consequences:

1. Fresh v1.1 installation replays migrations `000001` through `000019`.
2. A v1.0.2 database requires the released chain plus `000015`-`000019`, according to its starting ledger.
3. Editing an applied migration causes checksum failure.
4. Removing an early file breaks clean bootstrap, contiguity/latest-version assumptions, rollback lookup, and the documented migration package contract even if a particular upgraded database already has a ledger row.
5. No replacement baseline/squash mechanism exists.

**Conclusion: every existing migration must remain embedded, in place, and byte-stable.** It is not safe to delete, archive out of the binary, rewrite, or squash old migrations for v1.1. A future baseline would require a designed runner feature, explicit support-baseline policy, fresh-install and upgrade proofs, backup/restore compatibility, and an append-only transition. No such work should be folded into hygiene cleanup.

Migration documentation has two active discrepancies: `docs/database/schema.md` stops its table at 000018 and describes only 000016-000018, while `docs/operations/compatibility-matrix.md` lists only 000016/000017 for the v1.1 upgrade. Migration 000019 is real and the release notes are more complete. Correct both documents before RC.
