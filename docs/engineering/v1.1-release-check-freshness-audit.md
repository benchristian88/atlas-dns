# Atlas DNS Controller v1.1 release-check freshness audit

Date: 2026-08-29 (Pacific/Auckland)

## Outcome and boundary

The AdGuard Home release-check worker had a confirmed scheduling defect. Its
six-hour wake cadence equalled the successful cache lifetime, while failed
evidence expired after 15 minutes. The correction changes only the worker wake
cadence to five minutes. The six-hour success lifetime, 15-minute failure
lifetime, cache row, API representation, and version-transition rules remain
unchanged.

The controller remains outside the DNS request path. Release-source failure
does not change node API health, DNS health, redundancy, certificate
applicability, desired state, deployments, authentication, or compatibility.
No migration or schema change is required.

## Confirmed state machine and defect

`ReleaseChecker.Refresh` reads the singleton AdGuard Home release-cache row.
When `now` is before `expires_at`, it returns without an upstream request.
Expired or missing evidence causes one bounded GitHub request. Success writes
validated version metadata with a six-hour expiry. Failure retains the prior
version and release URL, records an error with unknown compatibility, and uses
a 15-minute expiry.

The worker runs once at process startup. Before this fix it then woke every six
hours. If a successful request completed just after `T`, the cache could still
be valid at the `T+6h` worker pass, expire immediately afterward, and receive no
new opportunity until `T+12h`. A failure at `T` expired at `T+15m` but likewise
received no retry opportunity until `T+6h`. Restart appeared to repair either
case because startup supplied an immediate worker pass.

With a five-minute cadence, the maximum scheduler delay after either expiry is
one worker interval. Cache checks remain local until evidence expires, so the
new cadence is not a five-minute GitHub request cadence.

## Evidence behind classifications

- DNS freshness is deliberately `max(3I, 2m)`. The DNS scheduler uses the same
  live `I`, so it tolerates two missed schedules across the full 5-second to
  one-hour runtime range. Dashboard HA, HA summary, Operational Status, and
  maintenance preflight call the shared function. This is **SENSIBLE**.
- Node connectivity uses three live intervals in both presentations, but
  Operational Status has a one-minute minimum that the Dashboard envelope does
  not. At runtime intervals below 20 seconds the two pages can cross their
  presentation thresholds at different times. Both still have scheduler
  headroom, so this is a design-consistency watch item rather than a
  demonstrated expiry/scheduler defect.
- Observation freshness has at least three runtime intervals plus request
  timeout, and the drift worker never runs less often than every 10 seconds.
  Reconciliation observation is conditional on an active revision by design;
  missing evidence is explicit rather than treated as fresh.
- Statistics has two intervals plus request timeout, with a three-hour floor.
  Query Log has three intervals with a two-minute floor. Both write explicit
  failed attempts and retry on the next pass rather than allowing a shorter
  failure marker to expire without a retry opportunity.
- Query Log overlap is constructed from the startup interval and is not resized
  after a runtime interval change. Durable high-water checkpoints, bounded
  pagination, gap detection, and database deduplication still prevent a
  demonstrated same-class stale window. Live overlap recalculation remains a
  design note; runtime semantics were not changed in this RC fix.
- Certificate state is recalculated from stored expiry metadata on each DNS/HA
  pass, while failed observations produce unknown state and Operational Status
  separately exposes observation freshness. A dedicated certificate-evidence
  freshness field could make that coupling clearer, but no scheduler deadline
  currently equals or exceeds a certificate cache TTL.
- Notification retry deadlines are at least two minutes while the idle worker
  wakes every 15 seconds. Deployment and command executors drive their own
  bounded backoff directly, so retry expiry cannot wait behind a longer fixed
  scheduler.
- Retention workers can run late without making live evidence appear fresh or
  deleting data early. Repeated cleanup failures retain extra data and remain
  visible through worker health.
- Controller-update, blocked-services, and filter-list caches are
  request-driven. Their next access performs the refresh decision directly, so
  no independent scheduler can miss an expiry boundary.
- Return-to-service checks are synchronous and actively collect their required
  evidence. They do not wait for a cached freshness deadline.

Restart behavior is coherent across the scheduled collectors: release, node,
DNS, inventory/drift, Statistics, Query Log, retention, and session cleanup
workers all receive an immediate startup opportunity. Durable checkpoints and
observations remain the source of truth across restarts.

No additional same-class timing defect was identified. The watch items above
do not justify threshold or runtime-setting changes on this RC branch.
